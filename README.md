# ecommerce-orders-analysis

Исследование заказов интернет-магазина: техническая очистка, разведочный анализ,
сравнение бейзлайнов и прогноз **количества уникальных заказов в день** с помощью
`HistGradientBoostingRegressor`.

Четыре оригинальных ноутбука сохранены без изменений. Данные подготовлены отдельным
скриптом; модель и контекст для инференса сохраняются в `models/model.joblib`.
Графики исследования выгружены в `reports/figures/`.

## Исследование

1. [Техническая проверка данных](notebooks/1.%20Техническая%20проверка%20данных.ipynb):
   очистка названий, пустых столбцов и строк, маркеров пропусков, чисел и дат.
2. [EDA](notebooks/2.%20EDA.ipynb): временное разбиение, пропуски, распределения,
   категории, способы оплаты, статусы и динамика заказов.
3. [Baseline](notebooks/3.%20Baseline.ipynb): значение в тот же день прошлого года
   и среднее дневное число заказов обучающего периода.
4. [Модель](notebooks/4.%20Модель.ipynb): пуассоновский градиентный бустинг,
   рекурсивный прогноз и permutation importance.

Данные содержат 584 524 позиции и 408 782 уникальных заказа.
Число строк не равно числу заказов. Цель учитывает все статусы, включая отмены.

| Выборка | Период | Строк |
|---|---|---:|
| Train | 2016-07-01 — 2017-12-07 | 413 754 |
| Validation | 2017-12-08 — 2018-03-27 | 83 496 |
| Test | 2018-03-28 — 2018-08-28 | 87 274 |

Границы выбраны по накопленным 70% и 85% уникальных заказов. Заказы между
выборками не пересекаются. Подготовка данных воспроизводит размеры и даты ноутбука.

На train категория `Mobiles & Tablets` лидирует по сумме `qty_ordered` — 92 883
единицы; далее `Men's Fashion` — 79 713 и `Superstore` — 58 218.
Это заказанные единицы без фильтра по успешной продаже.
Чаще всего в строках встречается оплата `cod` — 210 530 случаев.
Связь способа оплаты со статусом статистически значима, но слаба:
Cramér's V = 0,181. Частоты рассчитаны по позициям, а не уникальным заказам.

## Модель и результаты исследования

Признаки: день недели, месяц, выходной, циклические недельные и годовые компоненты;
лаги 1/7/14/28 дней; среднее и стандартное отклонение за 7/28 предыдущих дней;
числовые дневные агрегаты, числа уникальных категориальных значений и число строк,
сдвинутые на один день. Полностью пустые признаки удаляются по train.
В сохранённом запуске использовано 68 признаков.

Параметры: `loss="poisson"`, `learning_rate=0.03`, `max_iter=500`,
`max_leaf_nodes=15`, `min_samples_leaf=10`, `l2_regularization=5`, `random_state=42`.

Ниже **метрики из сохранённых выводов ноутбуков**, а не нового запуска скриптов:

| Метод | Выборка | MAE | RMSE | R² |
|---|---|---:|---:|---:|
| Тот же день прошлого года | Validation | 344,48 | 746,63 | −0,070 |
| Среднее train | Validation | 413,59 | 721,74 | около 0 |
| HistGradientBoostingRegressor | Validation | 330,74 | 693,25 | 0,077 |
| HistGradientBoostingRegressor | Test | 235,31 | 488,33 | 0,239 |

На validation бустинг улучшает показатели относительно обоих бейзлайнов,
но объясняет небольшую часть изменчивости ряда. По сохранённой таблице
permutation importance первые признаки — `raw_Customer ID_nunique`,
`raw_qty_ordered_std`, `raw_grand_total_max`, `lag_1` и `day_of_week`.

При повторном обучении и оценке **без фактических будущих агрегатов** получены:

| Выборка | MAE | RMSE | R² |
|---|---:|---:|---:|
| Validation | 393,21 | 713,93 | 0,021 |
| Test | 331,42 | 531,52 | 0,099 |

Прогноз всего периода из одной точки оказался менее точным, чем сохранённые
результаты ноутбука. Протокол описан ниже; метрики сохранены в
`reports/metrics/evaluation.json`.

Проверены совпадение очистки с первым ноутбуком (значения и типы), размеры и
непересечение выборок, сохранение и загрузка модели, прогноз на семь дней
после train и после всей наблюдаемой истории. Для проверки кода предусмотрены три теста.
SHA-256 всех четырёх ноутбуков совпадает с исходным состоянием.

## Запуск

Проверенное окружение — Python 3.13. Версии пакетов зафиксированы по локальному
окружению; версии исходного запуска ноутбуков неизвестны.
Все команды выполняются из корня репозитория.

```bash
python -m venv .venv
```

Активация в PowerShell: `.venv\Scripts\Activate.ps1`;
в Linux/macOS: `source .venv/bin/activate`.

```bash
python -m pip install -r requirements.txt
```

Готовый артефакт позволяет прогнозировать сразу после клонирования, без CSV:

```bash
python -m src.inference --days 7 --output reports/predictions/forecast.csv
```

По умолчанию прогноз начинается сразу после конца train — 2017-12-08.
Для прогноза после последнего наблюдаемого дня передайте полную очищенную историю
с той же схемой и типами, минимум за 29 дней:

```bash
python -m src.inference --history data/processed/cleaned_types.parquet --days 7
```

`--history` заменяет сохранённый контекст, но не переобучает модель.
Результат — CSV со столбцами `date` и `prediction`, в единицах заказов в день.
Прогноз не округляется до целого.

```python
from src.inference import forecast

predictions = forecast("models/model.joblib", days=7)
```

Для повторного обучения поместите исходный файл в `data/raw/test.csv`:

```bash
python -m src.prepare_data
python -m src.train --evaluate
```

Подготовка создаёт `cleaned_types.parquet`, `train.parquet`, `validation.parquet`,
`test.parquet` в `data/processed/`. Обучение сохраняет модель, порядок признаков
и контекст истории вместе в `models/model.joblib`. Используется только train.
Артефакт также содержит версии библиотек и SHA-256 обучающей выборки.
Загружайте через joblib только доверенные файлы. Папка `reports/predictions/`
создаётся при запуске инференса и не входит в Git.

```bash
python -m unittest discover -s tests -v
```

## Ограничения и протокол оценки

- В ноутбуке 4 `test_comparison` используется без создания, а `plt` — без импорта.
  Чистый запуск всего ноутбука не завершится успешно. Оригинал оставлен неизменным;
  отдельные скрипты не зависят от скрытого состояния Jupyter.
- Исходная оценка использует фактические агрегаты train, validation и test,
  сдвинутые на день. Внутри многодневного горизонта это данные, неизвестные
  на момент начала прогноза. Поэтому метрики выше не подтверждают качество
  прогноза всего горизонта из одной точки. Код получения test-прогноза отсутствует.
- Новый `train --evaluate` оценивает весь validation из конца train, затем test
  из конца наблюдаемого validation, без переобучения. Истинные агрегаты внутри
  горизонта не используются: неизвестные значения остаются NaN, что поддерживает
  модель. Это другой протокол; новые метрики сохранены отдельно в
  [reports/metrics/evaluation.json](reports/metrics/evaluation.json).
- Для многодневного инференса агрегаты доступны только на первом шаге, а лаги
  постепенно заполняются собственными прогнозами. Для ежедневного обновления
  передавайте свежую историю и прогнозируйте на один день.
- Исходная permutation importance использует фактические лаги validation;
  это другой режим относительно рекурсивного прогноза. Статусы и другие поля
  могут обновляться после даты заказа; их доступность на дату прогноза не проверена.
- Ноутбуки используют относительные пути. Для просмотра установите зависимости
  из `requirements-notebooks.txt`. Для ручного запуска первых трёх в их папке
  нужны локальные копии входных файлов. Для полного цикла используйте `src`.

Данные исключены из Git, но остаются локально. Внешний источник и лицензия датасета
не установлены по материалам исследования. Описание файлов и схемы:
[data/README.md](data/README.md).
